# Root 操作安全协议

版本: 1.2.0（随插件版本发布）
适用范围: AI 助手在本设备上执行的一切 root 及高权限 shell 操作
维护方式: 本文件为常驻协议。AI 在每次 L2 / L3 操作前应重新读取本文件，不依赖上下文记忆。

---

## 0. 基本前提

- 本文档面向已授予 root 权限的 AI 助手使用场景。
- root 权限本身没有路径级白名单，具备能力强弱之分，但不具备「只能改某个目录」的天然边界。
  因此「不改系统」不能只靠承诺，需要三层共同保证：
  1. **能力裁剪**：root 管理器（如 KernelSU）的模板机制，只授予必要能力
  2. **流程约束**：本协议规定的操作分级与审批
  3. **演习验证**：在正式使用前确认约束真实有效

- **权能说明**：建议只授予 `DAC_OVERRIDE`、`DAC_READ_SEARCH`、`FOWNER`、`CHOWN` 四类能力，
  并启用防二次提权标志。不应授予 `SYS_ADMIN`、`SYS_MODULE`、`SYS_BOOT`、`SYS_RAWIO`、
  `SYS_PTRACE`、`NET_ADMIN` 等能力。
  具体授予哪些位以 root 管理器实际模板为准，不要假定默认值。

- **关于 `NoNewPrivs` 读数为 0**：部分 root 管理器（如 KernelSU）使用私有语义实现防提权，
  不会写入内核标准 `no_new_privs` 位。因此 `/proc/<pid>/status` 中该字段读数为 0 **属于预期现象**，
  不能作为「模板失效」的判定依据。应以模板落盘文件中是否包含相应标志为准。

- 用户侧应保持「一键撤回授权」通道随时可用。

- 若当前无系统备份条件，不可逆操作一律按最高警戒处理。

### 数据访问通道

root 会话中的 `/data/data` 可能是**隔离视图**（空壳），无法直接看到其他应用的目录。
若遇到这种情况，第三方应用数据可通过以下通道访问：

```
/data_mirror/data_ce/null/<用户号>/<包名>/     # 对应 CE 存储
/data_mirror/data_de/null/<用户号>/<包名>/     # 对应 DE 存储
```

用户号通常为 `0`（机主），多用户或分身环境为 `10` 及以上。
操作前应确认实际路径，不要假定用户号。

## 1. 权限自检

每次会话的首次 root 操作前执行：

```sh
id
grep -E '^(Uid|Gid|Groups|Cap(Inh|Prm|Eff|Bnd)|NoNewPrivs)' /proc/self/status
```

三查（全部通过才继续）：

1. **身份**：预期 `uid=0`。若不为 0，停止并报告通道异常。
2. **允许集校验**：`CapEff` 的置位应当**只包含**模板允许的能力，多出任何一位都要停下复核。
3. **禁止位黑名单**：以下能力任一置位即立即停止一切写操作并报告：
   `NET_ADMIN` / `SYS_MODULE` / `SYS_RAWIO` / `SYS_PTRACE` / `SYS_ADMIN` / `SYS_BOOT` / `MAC_ADMIN`

补充：核对 `CapBnd` 与 `CapEff` 是否一致；不一致时停下报告。

- 多用户注意：目标应用数据可能在 `/data/user/0`（机主）或 `/data/user/10` 及以上（分身 / 工作资料）。
  操作前确认实际路径。

## 2. 操作分级

| 级别 | 定义 | 处理方式 |
|---|---|---|
| **L0** | 只读：`ls` / `cat` / `stat` / `grep` / 哈希校验 / 查进程 | 直接执行 |
| **L1** | 可逆写：在应用私有目录或专用沙箱内新建、删除自己刚建的文件 | 直接执行 + 日志 |
| **L2** | 高风险但可恢复：修改第三方应用存档、批量文件操作（≥5 个文件）、配置替换、权限修改 | 备份原件 → 报告计划 → 用户批准 → 执行 → 复验 |
| **L3** | 高危不可逆：系统分区写入 / 挂载、格式化、分区表、刷机、绕过回收站的真实删除、批量删除 ≥20 个文件、任何写系统目录的操作 | **AI 只出「执行卡」，由用户亲手执行** |

补充规则：

- 系统路径的**只读**访问属 L0；**任何写意图**归入禁写区（见 §4）。
- 对「内容不确定的第三方数据」的删除，一律按 L2 起步。
- 用户说「直接做」也不改变 L3 的定义——L3 永远只出执行卡。
- **L3 执行卡规范**：必须包含【目标 / 命令 / 预期结果 / 回滚方式 / 中止条件】，
  并附「逐行核验后再执行」提醒；禁止包含通配符批量命令；生成后不得由 AI 代为执行。

---

## 3. 标准操作流（以修改第三方应用存档为例）

1. **侦察**（L0）：确认目标文件存在、大小 / 属主 / 权限，确认目标应用是否在运行
2. **声明**：向用户报告【目标路径、操作、预期结果、回滚方式】
3. **备份**：原件复制到备份区，保留属主与权限信息，记录账本
4. **执行**：使用最小化命令，禁止通配符批量破坏命令，禁止直接使用 `rm -rf`
5. **复验**：校验结果（大小 / 内容比对 / 应用可读），与预期对照
6. **记录**：写操作日志（时间 / 命令 / 理由 / 结果）
7. **失败处理**：停止，不重试；报告并保留现场（备份不删）

## 4. 禁写清单

以下路径任何情况下不允许写入：

```
/system  /vendor  /product  /system_ext  /boot  /init_boot  /vbmeta
/persist  /efs  /metadata  /firmware  /modemst*  /fsg  /fsc
/data/system  /data/misc  /data/adb  /data/vendor  /data/apex
/dev/block/*          （任何裸块设备）
以及 /（根）与任何挂载点本身的创建 / 修改 / 删除
```

- 需要改动这些路径的操作（即使用户要求）：降级为 L3，只出执行卡
- 例外：root 管理器的自身目录可只读查看（L0）；写入仍需 L3 执行卡
- 对禁写清单的写意图，流程上一律直接拒绝（不下发、不试探）

## 5. 回收站机制

### 同卷原则

保证移动操作原子、瞬时、不产生半拷贝状态：

- 目标在 `/data` 卷 → 进入**系统层回收站**（应用私有目录）
- 目标在 `/sdcard` 卷 → 进入**用户层回收站**（共享存储约定目录）
- 脚本按目标路径所在分区自动选择；无法同卷时**拒绝操作**，不做跨卷移动

### 结构

```
<trash_root>/
├── manifest.log        # TSV: 时间 \t 原路径 \t 回收路径 \t 原因 \t 操作者
├── trash/<时间戳>_<文件名>
├── backups/<时间戳>_<文件名>
└── guard.log
```

### 规则

- **删除 = 移动进回收站 + 记账本**，绝不用裸 `rm`。真实删除属 L3
- **修改前备份**（只复制、不移动）：副本进 `backups/`，账本记录 `BACKUP:` 前缀
- **还原**：按账本匹配原路径与回收路径后才动；优先移动（保留属主 / 权限 / 安全上下文）；
  必须复制时应保留属性，并预案修复 SELinux 上下文
- **保留期**：建议 ≥30 天或经用户明确批准才清理（清理属 L2）
- **无自动过期**：回收站不会自动清理，需定期检查占用

### 脚本强制层

不依赖 AI 自觉，脚本自身拒绝危险形态：

- 拒绝：空参数 / 根路径 / 禁写清单路径 / 不存在的路径 / 含未展开通配符 / 多目标批量
- 单次只处理一个明确目标
- 所有动作追加账本与日志，不可静默

---

## 6. 日志

- 记录所有 L1 及以上操作：`ISO8601（含时区偏移） | 级别 | 命令 | 理由 | 结果`
- 日志与回收站同目录，便于统一备份
- 日志只追加，不覆盖、不删除；轮转由用户手动决定

---

## 7. 三重复核

0. **前置留痕**：L2 / L3 操作前重读本协议，并在回复中标注已重读（形成可见证据）
1. **写后核**：语法、路径拼写、引号转义、目标存在性（现场验证，不凭记忆）
2. **执行前核**：当前身份与权能、前置条件、副作用范围、目标是否仍符合预期
3. **执行后核**：实际输出与预期对照；不一致立即停、报告、保留现场

---

## 8. 硬性禁止

- 禁止直接使用 `rm -rf`（任何路径）
- 禁止对未验证存在性的路径做删除
- 禁止在路径或变量中混用通配符做批量删除
- 禁止对未知内容的目录做「清空」操作
- 禁止修改系统版本、OTA、基带相关的任何文件
- 禁止使用 `dd` / `mkfs` / `fastboot` / `mount -o rw,remount` 类命令（这些属 L3）
- 禁止在未声明目标的情况下执行写操作
- 禁止做未被批准的额外操作（范围蔓延）
- 禁止盲目重试失败的命令（先停、查因、报告）

## 9. 消防演习清单

正式使用前应完成以下验证：

| # | 项目 | 预期结果 |
|---|---|---|
| 1 | 身份与权能自检（按 §1） | 全部通过 |
| 2 | 沙箱写测试：写 → 读 → 校验 | 哈希一致 |
| 3 | 回收站闭环：建测试文件 → 进回收站 → 核对账本 → 还原 → 核对 | 全链路一致 |
| 4 | 负向测试 A：沙箱内尝试挂载 tmpfs | 权限拒绝（证明无挂载能力） |
| 5 | 负向测试 B：尝试写系统分区 | 只读拒绝（证明物理只读） |
| 6 | 流程拒绝测试：对禁写清单 / 空参数 / 通配符分别调用 | 全部拒绝、零副作用 |
| 7 | 日志核查：账本字段完整、格式规范 | 通过 |
| 8 | 复验：清理沙箱，回收站与日志状态干净 | 通过 |

约定：演习应使用固定沙箱路径，不得使用其他位置；任何失败项需停下报告、修复后重演；
全部通过才允许执行第一个真实任务。

## 11. 应急流程

1. **立即停手**：停止一切进行中的写操作，不再执行任何新命令（尤其不要「再试一次」）
2. **报告**：向用户说明【发生了什么 / 影响范围 / 当前状态】，主动上报不等问询
3. **现场保护**：不删除任何痕迹（日志、回收站、半成品文件全部保留原样）
4. **可恢复优先**：误删除则从回收站还原；误修改则从备份恢复。
   恢复动作同样走「声明 → 批准 → 执行 → 复验」
5. **不可恢复上报**：若涉及禁写区或系统层，AI 不再动手，由用户决定后续处置
6. **复盘**：记录事件经过、根因、修复措施

应急流程中的红线：不掩盖、不缩小化、不擅自「补救」——补救动作也须用户批准。
